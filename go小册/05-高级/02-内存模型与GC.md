# 02 · 内存模型与 GC

两件相关的事：

1. **内存模型**：什么时候 goroutine A 的写入，B 一定看得见？
2. **垃圾回收**：堆上的对象何时被收回，STW 会停多久？

写对同步，程序才正确；理解 GC，优化才有方向。

---

## 1. Happens-before

Go 内存模型定义了若干 **happens-before** 关系。若「写 x happens-before 读 x」，读到的就是那次写（或之后的写）。没有这层关系，编译器和 CPU 都可以乱序，你可能读到旧值，race detector 会报。

常见建立 happens-before 的方式：

| 操作 | 关系 |
|------|------|
| 同一 goroutine 里语句先后 | 前面 happens-before 后面 |
| channel 发送完成 | happens-before 对应接收完成 |
| 关闭 channel | happens-before `v, ok := <-ch` 的 `ok==false` |
| `Mutex.Unlock` | happens-before 下一次成功的 `Lock` |
| `Once.Do(f)` 里 f 结束 | happens-before 任何 `Do` 返回 |
| `WaitGroup.Done` 减到 0 | happens-before `Wait` 返回 |
| `atomic` 的存储 | 与对应的载入有同步（按文档） |

**错误示范**：goroutine A 写 `ready = true` 和 `data = 1`，B 空转等 `ready` 再读 `data`。没有同步原语，B 可能永远看不见 `ready`，或看见 `ready` 却看不见 `data`。

```go
// 正确：用 channel 或 Mutex 或 atomic
done := make(chan struct{})
go func() {
	data = 1
	close(done)
}()
<-done
fmt.Println(data) // 一定是 1
```

初始化：包级变量初始化 happens-before `init`，所有 `init` happens-before `main`。跨包按导入图。

完整条文：[https://go.dev/ref/mem](https://go.dev/ref/mem)

## 2. 发布与逃逸（概念）

把一个对象的指针存进全局变量、channel、接口，其它 goroutine 就可能看见它。编译器因此常把该对象放到**堆**上（逃逸）。下一章细讲如何看逃逸结论；这里只要记住：**同步和生命周期决定对象在哪，不是你写没写 `new`。**

---

## 3. 堆、栈、分配器

- **栈**：每个 G 一块，可增长。局部变量没逃逸就在栈上，函数返回即失效（指针不会还给别人）。
- **堆**：GC 管理。`make`、闭包捕获、接口装箱、返回指针等常常上堆。

分配器是 **tcmalloc 风格**：P 有本地 mcache，按 size class 取 span，减少锁。这就是「P 上挂着内存缓存」的含义。

---

## 4. GC：三色标记 + 并发

极简图像：

1. **标记**：从根（全局、栈、寄存器）出发，顺着指针涂「存活」。
2. **清扫**：没涂到的回收，空间还给分配器。
3. 大部分标记与用户代码**并发**；需要短暂 **STW**（Stop The World）做启动、收尾、栈扫描协调。

现代 Go 的 STW 通常在亚毫秒到数毫秒量级（视堆和 goroutine 数量），不再是「停几百毫秒」的老印象。但：

- 堆很大、存活对象很多 → 标记更费 CPU。
- goroutine 极多 → 扫描栈更费。
- 分配极快 → GC 更勤。

`GOGC`（默认 100）表示「堆相对存活大小增长 100% 再触发」。`GOGC=off` 关闭自动 GC（几乎只用于基准）。Go 1.19+ 的 `GOMEMLIMIT` 给运行时一个软内存上限，帮助在容器里更早回收，减少被 OOM Kill。

```bash
GOGC=50 ./app           # 更勤快，CPU 换内存
GOMEMLIMIT=512MiB ./app
```

程序里：`runtime.GC()` 强制一次（测试或基准隔离时用）。`debug.SetGCPercent`、`debug.SetMemoryLimit` 对应上述变量。

## 5. 最终器与不用它的理由

```go
runtime.SetFinalizer(p, func(p *T) { p.close() })
```

执行时机不确定，且可能拖到进程退出都没跑。资源释放请用 `defer Close`，不要靠 Finalizer。它偶尔用于「发现泄漏时打日志」。

---

## 6. 怎么观察

```bash
GODEBUG=gctrace=1 ./app
go tool pprof http://.../debug/pprof/heap
go tool pprof -alloc_space ...   # 看分配总量而不只是残留
```

`runtime.ReadMemStats` 能读 `HeapAlloc`、`NumGC`、`PauseTotalNs`。服务里用指标导出这些，比猜「是不是 GC 导致延迟」有效。

---

## 7. 和正确性的边界

GC **不修复数据竞争**。它只保证：还被引用的对象还在，没被引用的终将消失。野指针、用 `unsafe` 藏指针、在 `uintptr` 里跨函数存地址，GC 可能收掉对象，程序随机崩。

写对并发：用内存模型里的同步。  
写好性能：减少不必要的堆分配（下一章），给容器设 `GOMEMLIMIT`，用 pprof 而不是感觉。
