# 04 · 错误处理

Go 把失败当成普通值来传。好处是控制流看得见；代价是 `if err != nil` 会重复。写好错误处理，比再学一个语法点更影响代码质量。

---

## 1. error 只是接口

```go
type error interface {
	Error() string
}
```

任何带 `Error() string` 的类型都是错误。构造：

```go
errors.New("not found")
fmt.Errorf("open %s: %w", path, err) // %w 包装
```

成功必须返回 `nil` 接口，不要返回「类型非空、值是 nil」的指针，见上一章。

---

## 2. 返回约定

```go
func Find(id string) (User, error) {
	if id == "" {
		return User{}, errors.New("empty id")
	}
	u, err := repo.Get(id)
	if err != nil {
		return User{}, fmt.Errorf("find user %s: %w", id, err)
	}
	return u, nil
}
```

- 失败：零值 + 非 nil error。
- 成功：有效值 + nil。
- 不要「半成功」：`return u, err` 在 err 非 nil 时让调用方猜 u 能不能用。少数 API（如 `io.Reader`）故意允许 `n>0 && err!=nil`，必须在文档里写死。

---

## 3. 包装、判断、拆开

Go 1.13+ 的标准动作：

```go
var ErrNotFound = errors.New("not found")

func (r *Repo) Get(id string) (User, error) {
	// ...
	return User{}, fmt.Errorf("user %s: %w", id, ErrNotFound)
}

u, err := repo.Get(id)
if errors.Is(err, ErrNotFound) {
	// 处理「没有」
}
```

`errors.Is(err, target)` 会沿着 `%w` 链找。不要用 `err == ErrNotFound`，包装后就不相等了。

自定义类型：

```go
type HTTPError struct {
	Code int
	Err  error
}

func (e *HTTPError) Error() string {
	return fmt.Sprintf("http %d: %v", e.Code, e.Err)
}

func (e *HTTPError) Unwrap() error { return e.Err }

var he *HTTPError
if errors.As(err, &he) {
	fmt.Println(he.Code)
}
```

- `Is`：和哨兵错误比。
- `As`：抽出链上某种类型。
- `Unwrap`：让包装可被遍历。`fmt.Errorf("%w", err)` 自动实现。

**不要用字符串包含来判断错误**（`strings.Contains(err.Error(), "not found")`），文案一改逻辑就断。

---

## 4. 哨兵、类型、不透明，三种风格

| 风格 | 做法 | 适用 |
|------|------|------|
| 哨兵 | `var ErrXxx = errors.New(...)` | 稳定、少、跨包判断 |
| 类型 | 自定 struct + `As` | 需要带 Code、Path 等现场 |
| 不透明 | 只包装，调用方不判断 | 内部失败，上层统一记日志/返回 500 |

导出错误要克制。一旦导出 `ErrNotFound`，它就成了 API。包内部的琐碎失败保持不透明更好。

---

## 5. 多个错误（1.20+）

```go
err := errors.Join(err1, err2)
// 或
return fmt.Errorf("cleanup: %w; close: %w", errSave, errClose)
```

`errors.Is` / `As` 会检查 Join 里的每一个。关闭资源时「主错误 + Close 错误」很常见：

```go
func slurp(path string) (data []byte, err error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer func() {
		if cerr := f.Close(); cerr != nil {
			err = errors.Join(err, cerr)
		}
	}()
	return io.ReadAll(f)
}
```

这里用了命名返回值，才能在 defer 里改 `err`。

## 6. panic 不是错误处理

`panic` 用于：

- 程序 bug（数组越界、nil 指针、不可能的分支）
- 初始化失败且无法继续（`main` 里配置都读不到）
- 必须立刻停（极少）

不要用 panic 表达「文件不存在」「用户输入非法」。库函数尤其不要 panic，除非写 `MustXxx` 并在名字里说清楚。

`Must` 模式：

```go
func MustAtoi(s string) int {
	n, err := strconv.Atoi(s)
	if err != nil {
		panic(err)
	}
	return n
}
```

只适合初始化或测试。请求路径上用回 `error`。

---

## 7. 怎么写错误文案

好：

```text
open config /etc/app.yaml: permission denied
decode user 42: unexpected end of JSON input
```

差：

```text
error
failed
something went wrong
```

原则：

1. 从外到内读起来是一条因果链（靠 `%w`）。
2. 带上关键标识（id、path、url），不要带密码、token。
3. 首字母小写、不加标点结尾，方便被再包装（官方风格）。
4. 给用户看的文案和给日志看的错误分开。HTTP 不要把内部 `err.Error()` 直接当响应。

---

## 8. 减少啰嗦，但不发明框架

可以接受的减轻方式：

- 提前返回
- 小函数把重复的「调用+包装」收起来
- 泛型辅助（克制）

不推荐：把所有函数改成 panic，再在顶层 recover；或引入「错误码全局表」替代 `error`。标准库和几乎所有优秀 Go 项目都还在写 `if err != nil`。
