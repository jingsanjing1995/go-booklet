# 06 · 并发模式与陷阱

前面的零件可以拼成几种反复出现的结构。这一章给「能抄的骨架」和「抄的时候别踩的坑」。原则仍是：有取消、有上限、有人等待、有人处理错误。

---

## 1. 工人池（限制并发）

```go
func Map(ctx context.Context, n int, jobs []Job, fn func(context.Context, Job) error) error {
	if n < 1 {
		n = 1
	}
	ch := make(chan Job)
	var wg sync.WaitGroup
	errOnce := make(chan error, 1)

	for i := 0; i < n; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for job := range ch {
				if err := fn(ctx, job); err != nil {
					select {
					case errOnce <- err:
					default:
					}
				}
			}
		}()
	}

	func() {
		defer close(ch)
		for _, job := range jobs {
			select {
			case ch <- job:
			case <-ctx.Done():
				return
			}
		}
	}()

	wg.Wait()
	select {
	case err := <-errOnce:
		return err
	default:
		return ctx.Err()
	}
}
```

要点：工人数固定；任务 channel 关闭后工人退出；错误至少留下一个；`ctx` 能打断投递。生产代码更建议 `errgroup` + 信号量。

信号量版：

```go
sem := make(chan struct{}, n)
for _, job := range jobs {
	sem <- struct{}{}
	wg.Add(1)
	go func(job Job) {
		defer wg.Done()
		defer func() { <-sem }()
		_ = fn(ctx, job)
	}(job)
}
```

## 2. 扇出 / 扇入

- **扇出**：一个任务分给多个 goroutine。
- **扇入**：多个 channel 合并到一个（上一章的 `merge`）。

```go
func fanOut(ctx context.Context, in <-chan Item, n int) []<-chan Result {
	outs := make([]<-chan Result, n)
	for i := 0; i < n; i++ {
		outs[i] = worker(ctx, in)
	}
	return outs
}
```

所有人读同一个 `in`，谁闲谁拿。关闭 `in` 让工人收工。

## 3. or-done 与超时包装

读一个可能再也不关的 channel，同时听取消：

```go
func orDone[T any](ctx context.Context, in <-chan T) <-chan T {
	out := make(chan T)
	go func() {
		defer close(out)
		for {
			select {
			case <-ctx.Done():
				return
			case v, ok := <-in:
				if !ok {
					return
				}
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		}
	}()
	return out
}
```

双重 select：避免 `in` 来了值却在 `out <- v` 上永远卡住。

## 4. 心跳与监督

长寿命工人定期往 `heartbeat` 发时间戳；监督者超时没收到就认为它死了，取消并重启。服务健康检查、websocket ping 都是变体。记得：心跳 channel 用缓冲 1 + 非阻塞发送，避免工人被慢监督拖死。

## 5. errgroup 模式（推荐日常使用）

```go
g, ctx := errgroup.WithContext(ctx)
g.Go(func() error { return listenHTTP(ctx) })
g.Go(func() error { return listenGRPC(ctx) })
g.SetLimit(16) // 可选：限制同时 Go 的数量
return g.Wait()
```

第一个非 nil error 会取消 `ctx`，其它人应尽快返回。`main` 里等一组长期服务很合适。

模块：`golang.org/x/sync/errgroup`。

## 6. 陷阱清单

### 6.1 goroutine 泄漏

等一个永远不关的 channel、`time.After` 在循环里、忘了 cancel、HTTP 没 `Close` Body 导致读循环挂住。**每个 `go` 都要能回答：什么条件让它退出？**

### 6.2 向关闭的 channel 发送 / 重复关闭

所有权必须单一。多发送方时用 WaitGroup 等发送方结束，由**一个人** close。

### 6.3 复制锁、复制 WaitGroup

`go vet` 能抓一部分。结构体带锁就指针传递。

### 6.4 map 并发写

直接 fatal：`fatal error: concurrent map writes`。加锁或每 goroutine 私有 map 再合并。

### 6.5 忽略 `-race`

没有竞争检测的并发测试等于没测。CI 至少对单元测试开 `-race`（会慢，值得）。

### 6.6 在请求路径无限创建 goroutine

来一个请求 `go` 一百个下游，没有上限。用池或 errgroup.SetLimit。

### 6.7 在持锁时做慢 I/O

锁内调网络，所有人排队。先拷出需要的数据，解锁后再 I/O。

### 6.8 用 `time.Sleep` 当同步

测试里 `Sleep(10ms)` 会变成闪烁。用 channel、`WaitGroup` 或 `testing` 的同步，而不是靠运气。

### 6.9 忘记 `Close` 与 `Stop`

`http.Response.Body`、`os.File`、`time.Ticker`、`sql.Rows`。和并发叠加后表现为连接耗尽，不像「死锁」那么好认。

## 7. 一套自检问题

1. 有多少 goroutine？谁启动、谁等待？
2. 取消从哪来，传到哪去？
3. channel 谁关？关几次？
4. 共享的内存用什么同步？
